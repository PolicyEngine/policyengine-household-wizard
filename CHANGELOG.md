## [0.2.0] - 2026-10-22

### Added

- Add the inputs a charitable giving calculator needs. `USPersonIncomes` gains `tipIncome`, `nonQualifiedDividendIncome`, `shortTermCapitalGains` and `longTermCapitalGains` (losses negative). A new `USPersonExpenses` has `charitableCashDonations`, `mortgageInterest` and `realEstateTaxes`, sent as the PolicyEngine US inputs `charitable_cash_donations`, `home_mortgage_interest` and `real_estate_taxes`; `mortgage_interest` is a computed total that the federal interest deduction ignores, and the tests now keep it as a guarded total that no field may set. `tipIncome` (tips received as an employee) is sent as `tip_income` and also added to `employment_income`, because PolicyEngine US counts tips as wages. A new `tippedOccupationCode` is sent as `treasury_tipped_occupation_code`; tips can qualify for the 2025-2028 deduction only with a listed code, and `TIPPED_OCCUPATIONS` exports the 71 occupations of the final regulations (26 CFR 1.224-1(h), T.D. 10044). `validate()` flags negative expenses and tips, unlisted occupation codes, and tips without an occupation answer (`person.tippedOccupationCode.requiredWithTips`, which apps that do not ask about the deduction can treat as a warning). `normalizeLegacyDraft` reads the new fields, including a legacy `mortgage_interest` as the interest paid. The variable graph snapshot now comes from PolicyEngine US 2.2.1, where `ssi` is a total of `ssi_if_takes_up`; it is reviewed as safe to set, since nothing else reads that component.
- Add `publicPensionIncome` and `privatePensionIncome` to `USPersonIncomes`, sent as `taxable_public_pension_income` and `taxable_private_pension_income`. Some state rules in PolicyEngine US read those components. Collecting `publicPensionIncome` lets government-pension exemptions apply: on PolicyEngine US 1.764.6 (the live API) those are in Arizona, Idaho, Minnesota, Missouri and Nebraska, and 2.15.16 adds Alabama, Kansas, Louisiana, Massachusetts and New York. `normalizeLegacyDraft` reads the new fields and per-person `pension_income_annual`, `public_pension_income_annual` and `private_pension_income_annual`.
- Add validated wizard navigation, explicit selection advancement, visited-step tracking, and question/error focus hooks. Enforce existing completion predicates in `goNext`. Move editable review rows from `role="listitem"` to native buttons inside list items; role-based selectors should target the button. Expose edit triggers and current-answer descriptions in answer summaries.

### Changed

- `ssiAmount` is sent as `ssi` only when every person in the draft has an amount (0 included); otherwise the model computes everyone's SSI, and `validate()` reports `person.ssiAmount.requiredWhenAnyReceives` for each person without one. An entered 0 is always sent, as `takes_up_ssi_if_eligible: false`, which affects that person only. `isFullTimeStudent` is sent as `is_full_time_college_student` instead of `is_full_time_student`, and only from age 18: PolicyEngine US counts everyone aged 5 to 17 as a K-12 student by age. Rules for college students (for example SNAP's student rule, New Jersey's exemption for dependents attending college and Colorado's EITC student rule) now see flagged people aged 18 and over; flagged 18- and 19-year-old high school students are treated as college students.
- `toV1HouseholdPayload` now sends `pensionIncome`, a pension of unknown source, as `taxable_private_pension_income` instead of the `taxable_pension_income` total. The total left both components at zero, so rules that read the private component never saw it. For callers that keep using `pensionIncome`, results change in Missouri on PolicyEngine US 1.764.6, and in Alabama, Louisiana, Missouri and New York on 2.15.16 (single-filer profiles tested). The adapter also reads numeric strings as numbers and skips other amounts that are not finite numbers, so a `NaN` or a string in one field cannot corrupt another field that shares its variable.

### Fixed

- `normalizeLegacyDraft` no longer counts tips twice. A legacy `employment_income` or `earned_income` follows PolicyEngine US, where wages include tips, but it was copied into `employmentIncome`, which excludes them, while `tip_income` also became `tipIncome`; the V1 adapter then sent wages plus tips again (a Nevada server with $42,000 of wages including $12,000 of tips was sent $54,000). Tips now come out of a legacy wage total, so the payload's `employment_income` equals the legacy figure. A camelCase `employmentIncome` is read as the draft's wages without tips. The SSI take-up comment now notes that California computes its supplement from federal SSI, so an entered 0 raises it. `validate()` flags negative wages (`person.employmentIncome.negative`), which tips above a legacy wage total can leave. Links still drop tips and other fields `serializeDraft` has no key for; its docstring now says so.
- Publish releases through npm trusted publishing so CI does not require an authenticator one-time password.
- `toV1HouseholdPayload` no longer lets one person's answer override what PolicyEngine US computes for everyone else. policyengine-core stores each variable as one array for all people, so an input on a computed variable for one person gave everyone else its default: one adult reporting SSI zeroed the other adult's SSI (live, a CA couple aged 70: 8,946 each, then 600 and 0), and one person's `isFullTimeStudent` took K-12 status away from every other child in the household. Computed variables are now sent for every person or no one. `is_tax_unit_dependent` is sent for every person from `kind` (false for adults), so a third adult is no longer counted as a dependent only when no child is listed. `normalizeLegacyDraft` reads a snake_case `ssi_amount` of 0 (cliff-watch's default for "not asked") as not entered. `serializeDraft` keeps an SSI amount of 0, which is now an answer ("receives none"), so a shared link no longer turns a complete set of SSI amounts into an incomplete one. Flags that are neither true nor false are no longer sent as `{year: null}`, and `normalizeLegacyDraft` reads a null legacy flag as not answered. `validate()` numbers people within their kind ("dependent 1", not "dependent 3").
- Map `socialSecurityIncome` to `social_security_retirement` instead of the `social_security` total in `toV1HouseholdPayload`. PolicyEngine US sums `social_security` from its components, so the total input left SSDI from `ssdiAmount` out of Social Security and everything computed from it. It also left `social_security_retirement` at zero, so programs that count that component (for example, several state child care programs) now see retirement benefits they previously missed. `socialSecurityIncome` now holds retirement benefits only; put SSDI in `ssdiAmount`.
